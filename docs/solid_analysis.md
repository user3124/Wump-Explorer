# Анализ SOLID

Проведен осмотр кодовой базы проекта (исходное состояние: `Main.kt`, `CliManager.kt`, `Models.kt`, `Security.kt`). Ниже — нарушения принципов с конкретными сценариями изменения, на которых они проявляются.

## Нарушение SRP (Принцип единственной ответственности)

Принцип проверяем вопросом: *«по скольким независимым причинам придется менять этот код?»*

### Главный случай: функция `main` в `Main.kt`

За 70 строк `main` отвечает сразу за пять разных вещей:

| № | Ответственность | Где в `main` | Что заставит её менять |
|---|-----------------|--------------|------------------------|
| 1 | Аутентификация (поиск пользователя, сверка хэша) | строки 12–20 | смена алгоритма хэширования или способа хранения паролей |
| 2 | Авторизация (разбор действия, формат и существование ресурса, наследование прав по дереву `A.B.C`, лимит объема) | строки 22–67 | новое правило доступа |
| 3 | Работа с данными (прямые обращения к `Database.users/resources/permissions`) | строки 12, 36, 45 | смена хранилища (файл, БД) |
| 4 | Перевод результата в код завершения | каждый `exitProcess(N)` | смена интерфейса: GUI, Web, тесты |
| 5 | Завершение процесса | `exitProcess` в 8 местах | то же самое |

Дополнительно данные смешаны с моделями: объект `Database` лежит в `Models.kt` рядом с `User`, `Resource`, `Permission`. Изменение списка пользователей физически правит файл моделей.

Сценарии, на которых это ломается:

* **Другое хранилище.** Захотели читать пользователей из файла. Правим `Models.kt` (где лежат и сами модели) и `Main.kt` (где идут прямые обращения к `Database`). Правило наследования прав при этом легко задеть случайно: оно записано в одной функции с поиском в списке.
* **Другой интерфейс.** Захотели вызвать ту же проверку из GUI или из теста. Сделать это нельзя: первая же ошибка вызывает `exitProcess` и убивает весь процесс. Бизнес-правила нельзя использовать без консоли.
* **Другой алгоритм хэширования.** Правим то же место `main`, где лежит авторизация, и вынуждены перепроверять и её.

Тот же дефект есть и в `CliManager`: он одновременно (а) разбирает аргументы, (б) печатает справку через `println` и (в) завершает процесс через `exitProcess(1)` и `exitProcess(7)`. Если справку или код выхода надо поменять, правится класс разбора аргументов.

### Порядок переноса обязанностей

Идем **снизу вверх по зависимостям**: сначала переносим то, что ни от чего не зависит, затем то, что на него опирается. `exitProcess` убираем из `Main` в самую последнюю очередь, поэтому программа остается рабочей после каждого шага. После каждого шага запускаем `scripts/test.sh`, результат не должен меняться.

| Шаг | Что переносим | Куда | Почему именно сейчас |
|-----|---------------|------|----------------------|
| 1 | Модели | `domain/models/` | Ни от чего не зависят, чистый перенос. Нужны всем следующим шагам |
| 2 | Данные: `Database` из `Models.kt` | `infrastructure/database/InMemoryDatabase` | Отделяем данные от моделей. Сразу вводим интерфейсы `UserRepository`, `ResourceRepository`, `PermissionRepository`, чтобы сервисы зависели от них, а не от конкретной базы |
| 3 | Граница «результат проверки» | `services/AccessResult` | Нужен до переноса проверок: при переезде каждая проверка заменяет `exitProcess(N)` на `return AccessResult.XXX` |
| 4 | Хэширование | `services/SecurityService` | Самый независимый кусок логики, нужен аутентификации |
| 5 | Аутентификация (п. 1 таблицы выше) | `services/AuthenticationService` | Опирается на `UserRepository` и `SecurityService` (шаги 2 и 4) |
| 6 | Авторизация (п. 2 таблицы выше) вместе с правилом наследования прав | `services/AuthorizationService` | Опирается на репозитории; правило наследования живет здесь, а не в хранилище |
| 7 | Порядок проверок | `services/AccessControlService` | Склеивает аутентификацию и авторизацию; сам правил не содержит |
| 8 | Справка и разбор аргументов | `infrastructure/cli/` (`HelpPrinter`, `ParseResult`, `CliManager`) | Парсер перестает печатать и завершать процесс: он возвращает результат |
| 9 | Перевод результата в код и `exitProcess` | остается в `Main.kt` | Финал: `Main` только собирает компоненты и переводит бизнес-результат в код завершения. Это единственный файл с `exitProcess` |

## Нарушение OCP (Принцип открытости / закрытости)

### Что НЕ является нарушением

Строка `Action.valueOf(actionStr)` не нарушает OCP. Если добавить в `enum Action` значение `DELETE`, `valueOf` примет его без единой правки в `Main.kt`: имя берется из самого перечисления.

### В чем нарушение на самом деле

Принцип проверяем сценарием: *«добавляем новое поведение, что приходится править?»*

**Сценарий.** Правило: действие `WRITE` разрешено только для объема не больше **половины** лимита ресурса (`READ` и `EXECUTE` остаются как были).

В старом коде единственный способ — вписать условие внутрь цепочки проверок в `main`:

```kotlin
if (volume > currentResource.maxVolume) {
    exitProcess(8)
}
// добавляем:
if (action == Action.WRITE && volume > currentResource.maxVolume / 2) {
    exitProcess(8)
}
```

Приходится менять уже работающую функцию, через которую проходят все действия, и заново проверять `READ` и `EXECUTE`, хотя их поведение не менялось. Каждое следующее правило для действия — еще один `if (action == ...)` в той же функции. Поведение, зависящее от действия, расширяется правкой существующего кода — это и есть нарушение OCP.

### Как исправить: правило на каждое действие

Изначально в плане был интерфейс `Command` с методом `execute(...): Boolean`. При проработке выяснилось, что он не подходит: он только «выполняет» и отвечает да/нет, а нам нужно знать, *какая* проверка не прошла (коды 4–8). Кроме того, действие у нас ничего не исполняет, а лишь проверяется. Поэтому тот же замысел («отдельный класс на действие, вызываем полиморфно») реализуем интерфейсом с точным названием:

```kotlin
interface ActionRule {
    val action: Action
    fun isVolumeAllowed(resource: Resource, volume: Int): Boolean
}

class ResourceLimitRule(override val action: Action) : ActionRule {
    override fun isVolumeAllowed(resource: Resource, volume: Int) = volume <= resource.maxVolume
}
```

`AuthorizationService` получает список правил и находит нужное по имени действия. Теперь сценарий из примера выглядит так:

```kotlin
class HalfLimitRule(override val action: Action) : ActionRule {
    override fun isVolumeAllowed(resource: Resource, volume: Int) = volume <= resource.maxVolume / 2
}
```

и в `Main.kt` одна строка регистрации меняется с `ResourceLimitRule(Action.WRITE)` на `HalfLimitRule(Action.WRITE)`. Код `AuthorizationService`, а значит и проверки `READ`/`EXECUTE`, не затрагивается. Сборку правил в одном месте (`Main`) считаем нормальной: это точка, где программа собирается целиком.

Ограничение: новое *значение* `Action` по-прежнему требует правки перечисления и регистрации правила. Это данные, а не логика, и для задачи этого достаточно.

## Итоговый план рефакторинга

1. Разнести ответственности `main` в порядке из таблицы выше (шаги 1–9).
2. Убрать вывод справки и `exitProcess` из `CliManager`: парсер возвращает `ParseResult`, справку печатает `HelpPrinter`.
3. Заменить проверку объема, завязанную на `main`, правилами действий `ActionRule`.
4. Сервисы возвращают `AccessResult`, `Main` переводит его в код завершения.
